# SmartHealth Agent：简历描述与面试表达

本材料基于 2026-09-09 的当前实现及验证记录。推荐将项目主线写为“领域工具服务化、受控 Agent 执行、证据与发布检查、系统评测”。完整技术材料见 [项目报告](project_report.md)。

下列句子是可用于项目经历的写法，请按实际承担的工作选择“设计并实现”“负责”或“参与”，项目时间和团队角色按真实情况填写。当前材料不推断本人在中国移动的任职、合作身份或线上交付经历。

## 1. AI Agent / AI Engineer 岗位推荐版

**SmartHealth Agent｜生理数据分析与多 Agent 报告系统**\
技术栈：Python、FastAPI、Pydantic、LightGBM、scikit-learn、Qdrant、ONNX Runtime、Tool Calling、SSE、Streamlit、pytest

项目简介：基于智慧家庭生理信号分析场景，重建数据分析工具并扩展为面向生产工程设计的 Agent 系统，实现从 CSV、异常预测到知识检索、报告审核和结构化输出的本地闭环。

- 设计 **Skills-Agent 两层架构**，将数据处理、异常预测、解释、检索和报告能力封装为 **9 个类型化 Skills**；通过 Pydantic 契约及 Registry 导出 Tool Calling schema，统一 RF/LightGBM 接口并复用训练与推理转换。
- 实现 **5 角色 ReAct Runtime** 与 simple/complex 路由，通过 YAML Harness 管理角色权限、调用预算和超时；支持任务幂等、取消、SSE 断线回放及按 run 关联的执行审计。
- 集成 **multilingual-e5-small ONNX + Qdrant RAG**，实现可定位证据、Writer/Safety 分工审核、分析/证据/草稿/策略版本绑定与有界修订，报告仅在发布检查通过后输出。
- 建立 Agent、RAG、Safety、System 四类评测及 **499 项自动化回归测试**；在真实领域模型与脚本决策基线中验证 **14/14 系统场景**，保留语义审核失败并生成可追溯的 JSON/Markdown 评测报告。

这版适合将重点放在 Agent Engineering，而不把合成模型高分放在第一句。14/14 的“脚本决策基线”限定应与数值一起保留；也可以只写评测规模，去掉通过率。

## 3. Machine Learning Engineer 侧重版

**SmartHealth Agent｜生理信号异常检测与可解释推理服务**\
Python / pandas / NumPy / scikit-learn / LightGBM / FastAPI / Pydantic

- 构建含心率、EDA、合成 EEG 代理及活动/睡眠上下文的 **57,600 行合成数据**，按 30 秒窗口提取 **35 维特征**；采用按用户独立划分的 train/validation/test，减少同用户窗口泄漏。
- 训练 RandomForest 与 LightGBM baseline，在验证集选择阈值；LightGBM 在 **12 个合成测试用户、384 个窗口**上取得 **F1 0.9714、ROC AUC 0.9978**，明确记录分数适用范围与数据生成假设。
- 设计 `BasePredictor` 和版本化模型包，统一训练/推理预处理，记录训练数据哈希，校验模型包完整性、特征顺序及依赖兼容性；应用启动加载一次模型并通过 FastAPI 提供预测与分析服务。
- 区分全局特征重要性与局部解释：使用 LightGBM 原生 `pred_contrib` 解释 raw margin，输出逐窗分数、关键贡献及图表，并通过类型化 Skills 供上层 Agent 调用。

这里的 57,600 是原始数据行数，经分窗后为 1,920 个训练/验证/测试窗口，不能写成 57,600 名用户或独立医疗病例。F1/AUC 必须保留“合成测试集”限定。

**SmartHealth Agent｜有界任务执行与 AI 工具服务平台**\
Python / FastAPI / Pydantic / httpx / Qdrant / SSE / pytest

- 设计稳定 Tool API 与类型化 Skill Registry，统一输入输出校验、异常处理、依赖注入和模型生命周期；通过 owner/session/input version 及产物来源关系约束临时引用访问。
- 实现独立于 SSE 连接的 Agent 任务生命周期，支持幂等提交、取消、有界事件回放及重启后的脱敏审计恢复；按 request/run ID 关联状态、调用耗时和模型版本。
- 通过 YAML 冻结策略、全局/角色预算、截止时间和有界执行池控制运行资源；超时后保留线程槽位并拒绝迟到写回，避免任务取消污染后续结果。
- 实现短期会话与 Qdrant 长期摘要的 TTL、可撤销 lease、归属过滤和删除，配套 **499 项自动化测试**；提供非 root Docker/Compose 与 GitHub Actions 配置，容器及远程 CI 待目标环境验证。

当前是单 API 进程和单主体开发认证，不应写成“已实现高并发分布式多租户平台”。重启恢复的是审计元数据，而不是恢复 LLM 执行或原始报告正文。

> 这个项目来自智慧家庭生理数据分析场景。由于原始代码和数据不可用，我围绕已有业务重新实现了数据分析工具，并进一步设计 Agent 层，让它具备可调用、可追踪和可评测的执行过程。
>
> 底层是 FastAPI 加 RF/LightGBM，训练和推理共用预处理与 35 维窗口特征。上层把能力封装成九个类型化 Skills，由五种角色通过 ReAct 循环选择动作。简单问题使用较短路径，复杂报告再进入分析、检索、写作和审核；角色权限、调用次数和超时由服务端 Harness 执行。
>
> 我重点处理了报告审核与内容绑定的问题：草稿、证据、分析结果和策略都有版本或哈希，修改草稿后必须重新审核，只有通过发布检查的正文才能进入 SSE。Memory 只长期保存受控摘要，历史内容不能代替当前数据或引用证据。
>
> 当前有 499 项自动化测试，以及真实 LightGBM、E5 和 Qdrant 的脚本决策基线。我也保留了一条语义审核失败，它说明来源正确和规则通过不等于主张得到支持。真实 LLM 后端已经有协议适配，但它的规划和审核效果还没有实测，这是下一项验证工作。

以上第一人称应与实际贡献一致。面试时优先选择一个自己能讲清楚实现、失败路径和测试的难点，不必一次列出全部技术名词。

## 6. 常见追问与回答要点

### 为什么需要 Agent，而不是固定 pipeline？

数据处理依赖保持确定性：新 CSV 必须先检查、清洗、提特征再预测。任务层则有不同需求：定义解释无需预测，展示历史结果可以复用，复杂报告需要检索和审核，失败后可能补充输入或修订。Agent 决定满足条件后的下一步，Runtime 校验能否执行。当前 scripted 示例只用来可复现地验证执行框架，真实 LLM 的动作选择质量还需评估。

### 这里的 Multi-Agent 是什么？

是共享引擎上的五种职责、上下文与权限分离的角色。Planner 可做一层委派，其他角色只能执行各自 Skills，预算属于同一 run。当前不是多模型集群，也不是多个微服务并行自动协商；采用同一个 LLM 后端时，Writer/Safety 也不具备统计独立的判断保证。

### 使用了哪个大模型？有没有真实调用？

当前实现兼容 Chat Completions function-calling 协议的决策适配器，模型和服务地址由管理员配置。已有集成和评测使用脚本角色，外部请求数为 0；真实运行的是 LightGBM、E5 ONNX 和 Qdrant。可以说明协议、执行约束和错误处理已经实现，但不能声称某个未配置的大模型已经完成效果验证。

### RAG 如何减少无依据的报告内容？

检索结果带证据 ID、来源、定位、内容哈希和版本；Writer 只能引用实际取得的证据，Safety 判断逐条支持关系，服务端检查分析/证据/草稿/策略绑定。但检索相似度不等于证据支持度；现有负例证明规则仍可能放行语义错误。后续需要真实审核后端及更大盲测集合，不能回答“已经消除幻觉”。

### 风险分数是什么？为什么不用准确率作为主要成果？

它是合成异常模型的窗口分数，会话取最大值，不是患病概率。当前使用按用户划分的独立测试集并报告 AP、AUC、F1；高指标主要证明当前生成器上的学习效果。没有真实临床标签，所以简历更适合强调数据划分、训练推理一致性、模型版本和解释契约。

### 是否可以直接扩容上线？

当前任务、预算、短期会话和临时产物由单进程持有，本地 Qdrant 也不能多进程共享同一目录。扩容需要可信身份、独立向量服务、共享会话/任务状态及 worker 协调，并验证幂等、取消和发布行为；直接增加 Uvicorn worker 不可行。Docker 配置已经提供，构建运行尚未验证。
